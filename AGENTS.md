# AGENTS.md

## What this is
Ruby LSP add-on (working name `ruby-lsp-yard`) that reads YARD `@param`/`@return` tags as type annotations for completion, hover, signature help and definition. Milestones M0–M7 are implemented: the add-on activates through `lib/ruby_lsp/ruby_lsp_yard/addon.rb` (gated by `depend_on_ruby_lsp!(">= 0.26.0", "< 0.28.0")`), all host-indexer access goes through `lib/ruby_lsp_yard/indexer/` (adapter interface + `RubyIndexerAdapter` for 0.26 and `RubydexAdapter` for 0.27), YARD parsing and the signature store live in `lib/ruby_lsp_yard/documentation/` and `signature_store.rb`, the M2 inference engine in `lib/ruby_lsp_yard/inference/`, the M3 RBS bridge and gem cache in `lib/ruby_lsp_yard/rbs/` and `lib/ruby_lsp_yard/gems/`, the hover/completion/definition listeners in `lib/ruby_lsp_yard/listeners/`, the M4 comment authoring patch, context detection, completion, type lookup and skeletons in `lib/ruby_lsp_yard/authoring/`, the M5 diagnostics linter, scanner and rules in `lib/ruby_lsp_yard/diagnostics/`, the M6 NodeContext shim in `lib/ruby_lsp_yard/host_context.rb`, and the M7 macro engine in `lib/ruby_lsp_yard/macros/`, domain registry in `lib/ruby_lsp_yard/domains/`, Solargraph config in `lib/ruby_lsp_yard/solargraph/`, inline `@type` annotations in `lib/ruby_lsp_yard/inference/annotations.rb`, `rbs collection` loading in `rbs/loader.rb` and `rbs-inline` in `rbs/inline.rb`. The `Documentation::SignatureBuilder` (extracted in M7) builds every signature, shared by the store and the macro processor.

`docs/requirements_v1.md` is the accepted V1 spec (architecture, milestones M0–M7, open decisions D1–D14) and the source of truth for scope and design. Read it before implementing anything. Key decisions already made: `yard` gem is a runtime dependency (parsing only, no Registry); all indexer access goes through an adapter because 0.26 has `RubyIndexer` and 0.27 has Rubydex; completion inside comments requires a version-guarded monkeypatch (D3); where RBS and YARD both describe a method, RBS wins. M3's implementation notes live in §8.1, M4's in §9.1, M5's in §10.1 and M6's in §11.1.

## Commands
- Setup: `bin/setup` (i.e. `bundle install`); per-version bundles: `BUNDLE_GEMFILE=gemfiles/ruby_lsp_0.27.gemfile bundle install`
- Full check: `bundle exec rake` — runs `test` then `standard`; this is what CI runs (`.github/workflows/main.yml`, Ruby 3.4/4.0 × `gemfiles/ruby_lsp_0.26.gemfile` and `gemfiles/ruby_lsp_0.27.gemfile`)
- Tests: `bundle exec rake test`
  - single file: `bundle exec rake test TEST=test/ruby_lsp/ruby_lsp_yard/test_addon.rb`
  - single test: add `TESTOPTS="--name=test_it_has_a_version_number"`
- Lint: `bundle exec rake standard`; autofix: `bundle exec standardrb --fix`

## Gotchas
- `Gemfile.common` holds the shared development dependencies. Each supported `ruby-lsp` minor gets its own `gemfiles/ruby_lsp_*.gemfile` and CI matrix leg; widening the supported range means adding a file there, not editing `Gemfile`.
- `sig/ruby_lsp/yard.rbs` is scaffold RBS (single file; path mirrors the module, not `lib`); no typecheck runs in CI.
- Ruby target is >= 3.4 (gemspec, `.standard.yml`); CI exercises 3.4 and 4.0.
- The add-on entrypoint calls `RubyLsp::Addon.depend_on_ruby_lsp!(">= 0.26.0", "< 0.28.0")`. On 0.27 (Rubydex) the add-on uses `global_state.graph`; on 0.26 it uses `global_state.index`.
- `ruby-lsp` is a development dependency (Gemfile/gemfiles), not a runtime dependency; add-ons declare compatibility with `depend_on_ruby_lsp!` instead (FR-M0-02).
- Backends must pass `test/support/adapter_contract.rb`; the Rubydex backend includes the same module (`test/ruby_lsp/ruby_lsp_yard/indexer/test_rubydex_adapter.rb`) and the unavailable backend's test file is skipped. Fixture files are real files under `test/fixtures/` because indexer entries read comments from disk. Rubydex normalization details (singleton `Foo::<Class:Foo>` owners, synthesized attribute writers, `#`-stripped comments, built-in ancestors) are documented in §11.1.
- M3 adds `rbs` as a runtime dependency. `lib/ruby_lsp_yard/rbs/` builds its own `RBS::Environment` (core + all stdlib) in a background thread because `RubyIndexer`'s `RBSIndexer` strips type information; `lib/ruby_lsp_yard/rbs/source.rb` is the only code that queries `RBS::DefinitionBuilder`, and lookups are memoized per class. This code is host-version independent and Rubydex reuses it.
- Gem signatures are cached at `~/.cache/ruby-lsp-yard/<schema>/<gem>-<version>.bin` (root injectable; tests pass a temp dir) and invalidated by a `Gemfile.lock` digest. Writes are batched (first signature immediate, then every 32 writes/2 s) and flushed on `deactivate`. `Marshal.load` has no class allowlist on Ruby 3.4/4.0, so the payload is trusted user-local state. FR-M3-07 (`rbs collection`) is deferred to M7.
- The signature store subscribes to the RBS loader and drops its caches when the environment becomes ready, so lookups served during the background load window are not pinned to their fallback. LSP tests that assert core types call `index_core(server)` and then `wait_for_rbs(server)`. `test/corpus/test_m3_corpus.rb` is the M3 acceptance corpus; `benchmark/rbs.rb` measures environment build and lookup latency.
- M4 comment features are a monkeypatch (D3): every prepended module lives in `lib/ruby_lsp_yard/authoring/patch.rb`, the only patch file, and it is applied only when `RubyLsp::VERSION` is in `Patch::TESTED_VERSIONS`. That list must be updated when bumping `ruby-lsp`: `test/ruby_lsp/ruby_lsp_yard/authoring/test_patch.rb` fails if the installed version is not listed. The patch's only private host internals are `RubyDocument`'s `@parse_result` comments (guarded probe) and `ClientCapabilities#apply_client_capabilities` (records `snippetSupport`). M5's quick fixes ride on the same `Requests::CodeActions` patch.
- M5 diagnostics register the `Diagnostics::Linter` as the formatter identifier `"yard"`; Ruby LSP 0.26 never auto-detects add-on linters, so the user must list it in `rubyLsp.linters` (documented in the README; 0.27 behaves the same). The linter scans the live document (not the indexer), runs cheap rules first behind a 100 ms budget, and returns nil/[] on any failure. `diagnosticRules` in the add-on settings maps rule names to severities or `false`; `# yard:disable Rule` in a definition's comment block suppresses rules for it. Mismatch rules only check YARD-sourced signatures: `Signature#source` is `:yard` by default, `:rbs` in `Rbs::Source`, and `Gems::Cache::SCHEMA_VERSION` is 2 to invalidate payloads written before the attribute existed.
- M6 adds a `HostContext` shim (`lib/ruby_lsp_yard/host_context.rb`): 0.27's `NodeContext#surrounding_method` is a `MethodDef` and singleton nesting markers are `<Foo>` instead of `<Class:Foo>`. Inference, the completion listener and `Engine#host_resolution` (which accepts both `Foo::<Foo>` and `Foo::<Class:Foo>`) go through it. `ENRICHMENT_LIMIT` is 300 so core classes keep the same enriched item set on both backends.
- The gemspec builds its file list from `git ls-files`, so new files must be tracked before `rake build`/`install`.
- M7 details: `@!macro` expansion is a port of `MacroObject.expand` in `macros/expander.rb` (YARD's Registry is never touched); named macros are catalogued from the adapter's `all_definitions`; attach macros resolve through `method_definitions` so `include`/`extend`/superclasses work. `@!domain` and Solargraph `@type` are scanned from raw comment text/source because YARD drops them. Inline `@type` needs the live document, which only exists for patched requests and the diagnostics linter (`Engine#with_document`). `rbs-inline ~> 0.14` is a runtime dependency, which pins `rbs` to `~> 4.0`; inline signatures outrank YARD but core RBS still answers first for core owners. `rbs collection` is auto-detected from the workspace root by `rbs/loader.rb`. M7 fixtures live in `test/fixtures/project/lib/{macros,domains,inline}.rb` and `test/fixtures/rbs_collection/`.

## Git Workflow
* Follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) for all commit messages: `<type>[optional scope]: <description>`
* **Allowed Types**: 
  * `feat` (new feature)
  * `fix` (bug fix)
  * `docs` (documentation)
  * `refactor` (code restructuring)
  * `test` (adding/updating tests)
  * `chore` (tooling/dependencies)
* **Example**: `git commit -m "feat(api): add user authentication endpoint"`
* **Validation**: Run `npx commitlint --from HEAD~1 --to HEAD` before finalizing changes if commitlint is configured.
